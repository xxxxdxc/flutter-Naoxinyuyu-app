脑机接口蓝牙通信协议 — 上位机开发指南
  适用设备：植入式刺激器 (Device Type 0x00)
  上位机平台：Android / iOS / Windows / macOS（需支持 BLE 4.2+）



一、通信架构概述
1.1 BLE 连接方式
植入式刺激器作为 BLE Peripheral（从设备），上位机作为 BLE Central（主设备）。

   蓝牙版本要求：BLE 4.2 及以上，支持 LE Secure Connections (LESC)

   配对方式：LESC Just Works（无 PIN 码配对）

   首选 PHY：LE 2M（2Mbps 物理层）

   MTU：最大 247 bytes

   GAP Data Length：251 bytes


1.2 连接参数
上位机应尽量满足设备端提供的 Preferred Connection Parameters：


 参数                                          推荐值

 最小连接间隔                                      15 ms

 最大连接间隔                                      15 ms

 Slave Latency                               30

 连接超时                                        4000 ms


  说明：15ms 连接间隔 + LE 2M PHY 可最大化吞吐量，降低实时数据延迟。

设备暴露两个 GATT Service：

1.4 上下行数据通道总结

 上位机 → 设备：         Write Config (GATT Write / Write Command)
 设备 → 上位机：         Device Notify (GATT Notify)       — 配置响应、状态上报
                    Stream Data (GATT Notify)           — 实时感测数据 (CMD 0xC0)
                    Storage Data (GATT Notify)          — 存储数据上传 (CMD 0xE0)


     Write Config 支持 Write Request（设备返回 GATT 错误码）和 Write Command（无响应）。

     正常通信建议使用 Write Request，上位机可感知 GATT 层错误（0x80~0x9F）。



二、数据包格式详解
2.1 整体帧结构 (PDU Frame)
上位机发送和接收的每一帧数据均遵循以下结构（所有多字节字段为大端序）：


 +----------------+----------------+----------------+----------------+------------
 ----+
 | Frame Control     |       Data Header   |     Data        |     (Optional)      |
 |     (2 bytes)     |       (8 bytes)     |   (0~232 bytes) | Auth Signature |
 |                   |                     |                 |     (28 bytes)      |
 +----------------+----------------+----------------+----------------+


加密模式下，Data Header + Data 区域被加密，并额外附加 28 字节 Authentication Signature。非加
密模式下无此字段。


2.2 Frame Control（帧控制，2 字节）

 Byte 0: Preamble (0xA5, 固定)
 Byte 1: [Rolling Counter(4bit)] [Encryption(1bit)] [AckReq(1bit)]
 [Reserved(2bit)]

2.6 Authentication Signature（可选，28 字节）
仅加密模式下存在：


 字段                字节数               说明

 MAC               16                ChaCha20-Poly1305 消息认证码

 Nonce             12                加密 nonce


2.7 Frame Control 字节编码速查
上位机构建 Frame Control 第二字节的方法：


 Byte1 = (RollingCounter << 4) | (Encryption << 3) | (AckReq << 2) | Reserved


 示例（非加密，需应答，RC=0）：
   Byte1 = (0 << 4) | (0 << 3) | (1 << 2) | 0 = 0x04
   全帧头 = [0xA5, 0x04]



2.8 大端序编码规则
所有多字节字段使用大端序（Big-Endian / Network Byte Order）传输。 包括但不限于：

   Timestamp（6 字节）

   PDU Length（2 字节）

   PDU Data 中的 u16 / u32 / float 等

上位机构建数据包时，务必使用大端序编码（如 Java 的
ByteBuffer.order(ByteOrder.BIG_ENDIAN) 、Python 的 struct.pack('>H', value) ）。


2.9 分包传输
当 Data 区超过单包承载能力时，需要分包：

   每个分包都带完整 Frame Control + Data Header

   Total Packet 填总分包数，Current Packet 填当前序号

   PDU 可以跨越分包边界：上一个包的 PDU Data 未完成部分，在下一个包的 Data 区继续，不重复
   opcode 和 PDU Length



三、安全认证流程
3.1 整体流程图

   App (Central)                                Device (Peripheral)
         |                                             |
         |<--------- BLE 连接建立 ------------------->|
         |<--------- LESC Just Works 配对 ------------>|
          |                                               |
          |--- CMD 0x01 Opcode 0x00 (安全状态查询) --->|
          |<-- has_private_key + is_app_trusted -------|
          |                                               |
          |   分支 A: 设备无私钥                                 |
          |--- CMD 0x02 Opcode 0x00 (传输私钥) -------->|
          |       [Secret Key 32B + Adata 4B]             |
          |<-- 0x00 Success/Fail ----------------------|
          |                                               |
          |   分支 B: App 未被信任                              |
          |--- CMD 0x02 Opcode 0x01 (App ECDH公钥) --->|
          |       [App Public Key 64B]                    |
          |<-- Device ECDH Public Key 64B -------------|
          |                                               |
          |   App: 计算 Shared Secret                           |
          |        = ECDH(App Private, Device Public)     |
          |                                               |
          |   Device: 计算 Shared Secret                        |
          |        = ECDH(Device Private, App Public)     |
          |                                               |
          |   App: Digest = HMAC-SHA256(Shared, Secret)   |
          |                                               |
          |--- CMD 0x02 Opcode 0x02 (发送摘要) ------->|

          |                                               |

          |                                               |
          |   Device: App 加入白名单                               |
          |                                               |
          |============= 安全通道已建立 ==================|
          |                                               |
          |   后续通信: ChaCha20-Poly1305 AEAD 加解密                |
          |   (Encryption Enabled = 1)                    |



3.2 安全状态查询 (CMD 0x01 Opcode 0x00)
方向：App → Dev（查询）

PDU：Opcode=0x00, Length=0, Data=空

响应 (Dev → App)：


 字节                   说明

 Byte 0               bit 0: 0=设备无密钥, 1=设备有密钥

                      bit 1: 0=App 未受信任, 1=App 已受信任

                      bit 2-7: 保留


上位机判断逻辑：
 if has_private_key == 0:
       执行 CMD 0x02 Opcode 0x00（传输私钥）
 elif is_app_trusted == 0:
       执行 CMD 0x02 Opcode 0x01（ECDH 公钥交换）→ Opcode 0x02（验证摘要）
 else:
       安全通道已就绪，直接进入业务通信



3.3 传输私钥 (CMD 0x02 Opcode 0x00)
前提：设备无密钥 → 需要设置（整个设备生命周期仅执行一次）

方向：App → Dev

PDU：Opcode=0x00, Length=36


             字节
 字段                  说明
             数

 Secret              上位机生成的 32 字节随机密钥，用作后续 HMAC 的 Secret。上位机必须
             32
 Key                 妥善持久化存储

 Adata       4       附加认证数据


响应：Opcode=0x00, Length=1，0=成功，1=失败


3.4 ECDH 公钥交换 (CMD 0x02 Opcode 0x01)
前提：设备已有私钥但 App 未受信任

方向：App → Dev

PDU：Opcode=0x01, Length=64，Data=App 的 ECDH 公钥（64 字节，secp256r1 曲线）

响应：Opcode=0x01, Length=64，Data=设备的 ECDH 公钥

上位机处理：


 app_private_key = 随机生成 secp256r1 私钥
 app_public_key = ECDH 公钥派生
 发送 app_public_key → 设备
 收到 device_public_key →
 shared_secret = ECDH(app_private_key, device_public_key)



3.5 摘要验证 (CMD 0x02 Opcode 0x02)
方向：App → Dev

PDU：Opcode=0x02, Length=32

Data：


 digest = HMAC-SHA256(key=shared_secret, message=secret_key)


即：用 ECDH 共享密钥作为 HMAC 密钥，对 Secret Key 计算 SHA256 摘要。

响应：Opcode=0x02, Length=1，0=验证通过（App 加入白名单），1=失败
3.6 数据加密 (ChaCha20-Poly1305 AEAD)
认证完成后，后续业务通信默认启用加密。

   加密算法：ChaCha20-Poly1305 AEAD

   加密范围：Data Header + Data 区域

   额外产物：28 字节 Authentication Signature（MAC 16B + Nonce 12B）

   计数器：设备端 dbs_get_counter() 在每次 BLE 连接初始化时重置

不需加密的例外：

   CMD 0x01（安全状态查询）

   CMD 0x02（安全状态配置）

   CMD 0xC0（实时数据上传，Stream Data）

上位机实现要点：

   加密模式下，Frame Control 的 Encryption Enabled 位 = 1

   解密时先验证 MAC（防篡改），再解密 Data Header + Data

   Nonce 由发送方生成，附在 Auth Signature 中



四、请求-应答模式
4.1 构建请求包流程

 1. 确定 Command（1 字节）
 2. 构建 PDU：Opcode (1B) + PDU Length (2B, 大端) + PDU Data (Length 字节)
 3. 拼接多个 PDU 到 Data 区
 4. 判断是否需要分包：
   - 加密模式：Data 区 ≤ 204 字节 / 包
   - 非加密模式：Data 区 ≤ 232 字节 / 包
 5. 构建每包：
   - Frame Control: 0xA5 + (RC<<4 | Enc<<3 | AckReq<<2 | 0)
   - Data Header: Timestamp + Total + Current + DataLen
   - Data 区
   - 若加密：Auth Signature (28B)
 6. 通过 GATT Write 发送到 Write Config Characteristic



4.2 解析响应包流程

 1. 从 Device Notify Characteristic 的 GATT Notify 中接收数据
 2. 检查 Preamble（第 1 字节必须是 0xA5），不匹配则丢弃
 3. 检查 Rolling Counter，与上次相同则丢弃（防重放）
 4. 提取 Encryption Enabled 位：
   - 若 = 1：验证 MAC → 解密 Data Header + Data → 提取 PDU
   - 若 = 0：直接提取 PDU
 5. 检查分包：
   - 若 Total > 1：缓存各分包，全部收齐后拼接 Data 区再解析 PDU
 6. 从 Data 区按序解析 PDU：读 Opcode → 读 PDU Length → 读 PDU Data
 7. 根据 Command + Opcode 分发到业务处理
4.3 GATT 层错误码
设备通过 Write Request 的 GATT Status Code 返回处理结果：


 GATT Status               含义

 0x00                      操作成功

 0x80                      Format Error：数据格式/长度/量程错误

 0x81                      Flash Error：存储错误，掉电恢复

 0x82                      State Error：状态不允许当前操作


4.4 超时处理
上位机应实现超时重试机制：

   请求发出后启动定时器（建议 3~5 秒）

   超时未收到响应则重试（最多 2 次）

   若仍无响应，断开连接并提示用户"设备无响应"

   注意 Rolling Counter 同步：重试前确认计数器值未被消耗

六、数据上传处理
6.1 CMD 0xC0 — 实时感测数据上传 ✅ 完整
通道：Stream Data Characteristic（Notify）

用途：设备定时（由 adc_process 触发）将实时感测数据推送到上位机。

加密：默认关闭（Stream Data 不加解密，以降低延迟）

PDU 格式：


 字段                   字节数              说明

 Opcode               1                0x00

 Length               2                PDU 数据长度（大端）

 Timestamp            6                第一个采样点的时间戳（前 4 秒 + 后 2 毫秒）

 Channel
                      2                bit0~15 = 通道1~16，1=开启
 Bitmask

 Datapoint            1                采样点数 N

                      ActiveCh × N     i16 数组（大端），顺序：ch1dp1, ch2dp1, ..., ch16dp1,
 Value Array
                      ×2               ch1dp2, ..., ch16dpN


上位机解析伪代码：


 active_channels = count_bits(channel_bitmask)         // 统计开启通道数
 total_values = active_channels * datapoint
 expected_data_len = 6 + 2 + 1 + total_values * 2         // 验证 Length


 values = []
 for dp in range(datapoint):
      for ch in range(16):
           if channel_bitmask & (1 << ch):
               value = read_i16_be(data, offset)
               values[(ch+1, dp)] = value
               offset += 2
行为注意：

    设备在发送 Stream Data 时会暂停广播以降低丢包率

    Notify 不带 ack，丢包不重传

    上位机应在连接建立后通过 CMD 0x0D Opcode 0x07 开启实时感测

七、典型工作流
7.1 完整连接→认证→配置→刺激控制→数据接收流程

阶段 1: BLE 连接
├─ 扫描设备（按 Service UUID 过滤或 Manufacturer Data 识别）
├─ 读取广播包获取设备状态（电量、温度、充电状态等）
├─ 发起 BLE 连接
├─ 设置 MTU = 247
├─ 设置 PHY = LE 2M
├─ LESC Just Works 配对
└─ 启用 Device Notify / Stream Data / Storage Data 的 CCCD


阶段 2: 安全认证
├─ 发送 CMD 0x01 Opcode 0x00（安全状态查询）
├─ 根据 has_private_key / is_app_trusted 判断：
│    ├─ 无密钥 → CMD 0x02 Opcode 0x00（传密钥）
│    ├─ 未信任 → CMD 0x02 Opcode 0x01（ECDH）→ Opcode 0x02（摘要验证）
│    └─ 已信任 → 跳过
└─ 安全通道建立，后续通信启用加密


阶段 3: 状态查询与配置同步
├─ CMD 0x03（本机状态）→ 记录硬件/固件版本、电量、温度、湿度等
├─ CMD 0x0C（运行模式）→ 记录当前开关状态
├─ CMD 0x04（用户数据查询）→ 获取患者信息
│    └─ 如需要，CMD 0x05 重新配置
├─ CMD 0x06（感测参数查询）
│    └─ 如需要，CMD 0x07 重新配置
├─ CMD 0x08（刺激参数查询，逐组 1~4）
│    └─ 如需要，CMD 0x09 重新配置
└─ CMD 0x0E（阻抗选项查询）


阶段 4: 刺激控制
├─ CMD 0x09/0x11（配置刺激参数）
│    └─ 先 0x0D 进入微调模式（可选）
├─ CMD 0x0D Opcode 0x01（选择当前编程组）
├─ CMD 0x0D Opcode 0x08（开启刺激器）
│    └─ 或 CMD 0x0D Opcode 0x00 综合设置
└─ 监控刺激状态变化（CMD 0x0C 主动上报）


阶段 5: 数据接收
├─ 实时感测：
│    ├─ CMD 0x0D Opcode 0x07（开启实时感测）
│    ├─ 监听 Stream Data Characteristic
│    └─ 解析 CMD 0xC0 数据包
├─ 存储数据同步（当前代码不可用）：
│    ├─ CMD 0x10 Opcode 0x00（开始同步）
│    ├─ 监听 Storage Data Characteristic
│    └─ 解析 CMD 0xE0 数据包
 └─ CMD 0x0D Opcode 0x07=0（关闭实时感测）


 阶段 6: 断开
 ├─ 停止刺激 → CMD 0x0D Opcode 0x08=0
 ├─ 关闭感测 → CMD 0x0D Opcode 0x07=0
 ├─ 断开 BLE 连接
 └─ 注意：实时感测/LFP 感测在断开后自动关闭



7.2 编程组定时切换工作流

 1. CMD 0x09（配置各编程组 1~4 的刺激参数）
 2. CMD 0x0D Opcode 0x05（设置定时计划）
   格式: ScheduleCount (u8) + n×[Start(u16 分钟) + Stop(u16 分钟) + Group(u8)]
   示例: 2 组定时
        Group1: 08:00-12:00 用编程组 1
        Group2: 14:00-18:00 用编程组 2
   → PDU Data = [0x02, 0x01E0, 0x02D0, 0x01, 0x0348, 0x0438, 0x02]
 3. CMD 0x0D Opcode 0x06=1（开启定时切换）
 4. 设备自动按计划切换，上位机可通过 CMD 0x0C 查询当前编程组




八、注意事项
8.1 空桩协议 — 避免使用
以下 Command 在代码中为纯占位函数（ return DBS_ERR_NONE ），无任何业务逻辑：


 Command                 函数                       影响

 0x0A                    控制参数查询                   返回成功但无数据

 0x0B                    控制参数配置                   返回成功但无效果

 0x0F                    保留                       返回成功但无效果


上位机应避免使用这些 Command，协议文档中 CMD 0x0A/0x0B 也标记为 TBD。


8.2 Flash 持久化全局未实现
ps_flash.c 的 flash_process 为空壳（ PROCESS_YIELD() 死循环），导致：

   CMD 0x05 / 0x07 / 0x09 / 0x11 / 0x0D / 0x0E 的配置修改仅在 RAM 中，设备掉电后丢失

   CMD 0x10 的存储数据同步实际上传不会发生

   CMD 0x00 Opcode 0x04（Clear Flash）可能无实际清理效果

   CMD 0x0E Opcode 0x04（同步历史阻抗结果）无法工作

上位机对策：每次连接后假设设备为出厂默认状态，重新下发全部配置。不要在 UI 中暴露"存储数据同
步"功能（当前不可用）。
8.3 大端字节序 — 必须严格遵守
所有多字节字段使用大端序传输，包括但不限于：

   数据包头部各字段

   PDU 中的 u16 / u32 / float / i16 / 时间戳

   时间戳结构（秒 4 字节大端 + 毫秒 2 字节大端）

常见错误：使用主机本地字节序（通常为小端序）直接写入，导致设备解析错误。


8.4 部分实现的 Command 使用限制

 Command       限制

               Factory Reset / Reboot / Remove Bonding / Clear Flash 在 RECOVER 阶段仅有删
 0x00
               密钥实际执行

8.5 安全相关注意事项
   CMD 0x02 严禁多 opcode 合并 — 必须逐条发送等待响应

   Secret Key（32 字节） — 上位机必须在本地安全持久化存储（如 Keychain / Keystore），丢失
   后无法恢复

   ECDH 私钥 — 每次认证时随机生成，无需持久化

   加密计数器同步 — 每次 BLE 连接后设备端计数器重置，上位机也需重置


8.6 状态互斥约束
上位机下发配置时应遵守以下约束（代码已校验，违反会返回 DBS_ERR_STATE）：

   测阻抗或充电时不可开启感测

   Motion 感测与实时感测互斥

   刺激运行时不可更改定时切换

   刺激运行时不可开始存储同步
